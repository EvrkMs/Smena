# Smena

Backend-сервер для закрытия смен на кассе: сотрудники передают отчёт о смене через Telegram-бота, сервер считает выручку, ЗП, движения сейфа и безнала, публикует итог в Telegram и хранит всё в Postgres. Отдельная root-панель (Razor Pages) — для администратора.

## Зачем это существует (история проекта)

Изначально фактические цифры по кассе (что реально в кассе/сейфе) могли расходиться с тем, что пробито в учётной программе. Разница закрывалась вручную: админы писали отчёт о смене прямо в Telegram, что регулярно приводило к ошибкам и требовало ручной проверки каждого отчёта.

Дальше эволюция шла так:

1. **Формат отчёта.** Договорились о фиксированном текстовом формате для Telegram, чтобы хотя бы было что проверять.
2. **Excel-таблица.** Ввод значений и подсчёт (выручка, ЗП, минусы) перенесли в Excel — уже не руками в столбик, но отправка отчёта в Telegram всё ещё оставалась ручной операцией.
3. **Первая программа.** Автоматизировали заполнение и отправку отчёта. Фото чека/экрана программы сотрудник всё ещё фотографировал на телефон и вручную прикладывал — неудобно.
4. **Запрос фото через бота.** Придумали механику: бот сам просит сотрудника прислать фото, сотрудник просто отправляет снимок боту, а тот прикрепляет его к отчёту. Тогда же появилась сущность **Employee** (сотрудник) — с часовой ставкой (чтобы автоматически вычитать ЗП из выручки) и Telegram ID, плюс отдельный `thread` (топик) в чате, чтобы отчёты не мешали остальным.
5. **Учёт сейфа.** Ручной подсчёт «блокнотом» стал неподъёмным (много факторов), поэтому добавили автоматический подсчёт сейфа: вся выручка из кассы уходит в сейф, кроме фиксированной суммы на размен (см. `ShiftRules.InitialCashRegister`).
6. **Переход на СУБД.** Пока данные жили в Excel, программа не имела серверной части и тормозила на каждом запуске (нужно было открывать таблицы). Отсюда — переход на нормальную СУБД: сначала MySQL, затем PostgreSQL (выбор в пользу простоты установки, а не принципиальных технических причин).
7. **Расчёт ЗП сотрудников.** Добавили отдельный Telegram-чат для зарплат с отдельной темой на каждого сотрудника — чтобы каждый видел свой баланс отдельно от общего потока.
8. **Расходы (Expenses).** Добавлены вместе с учётом сейфа — как отдельная операция, позволяющая списать наличные из сейфа с фиксацией причины, а не только пополнять его при закрытии смены.

Текущая версия сервера — результат этой цепочки решений. Часть архитектурных компромиссов в коде объясняется этой историей (например, почему сейф и ЗП считаются как append-only журнал операций, а не как редактируемое число).

## Как это устроено сейчас

### Стек
- **.NET / ASP.NET Core**, один процесс на два протокола:
  - gRPC (порт `5001`, HTTP/2 h2c) — API, которым пользуется клиент-бот/приложение кассира.
  - Razor Pages (порт `5000`, HTTP/1.1) — root-панель администратора (`/root`).
- **PostgreSQL** через EF Core (миграции применяются автоматически при старте, до `app.Run`).
- **Telegram.Bot** — единый бот-клиент и один общий `TelegramUpdatesPoller` (long polling) на всё приложение; фото запрашиваются через подписку на апдейты конкретного сотрудника.
- **МойСклад (MoySklad)** — опциональная интеграция для складского остатка (`Warehouse:Enabled`), с кэшем (`SkladCacheService`), обновляемым в фоне.
- Reverse-proxy (Caddy/Traefik в проде) не срезает префиксы `/panel` и `/grpc` — сервер сам перекладывает `PathBase` в middleware перед `UseRouting`.

### Домен

Ключевые сущности (`Smena/Services/Data/Entities`):

- **EmployeeEntity** — сотрудник: имя, часовая ставка, `SalaryThreadId` (тема в зарплатном чате), связанный `TelegramAccountEntity` (Telegram ID).
- **RaportEntity** + **RaportEmployeeEntity** — отчёт о закрытии смены: факт/программа по кассе и безналу, факт сейфа, комментарий к минусу, часы/минус/ЗП по каждому сотруднику смены.
- **SafeOperationEntity** — append-only журнал движений сейфа (`Coming`/`Expense`); текущий баланс — это `SUM` по журналу.
- **SalaryOperationEntity** — append-only журнал по ЗП сотрудника: `Regular` (смена), `Bonus`, `Advance`, `Inventory` (недостача), `Fine`, `Pay` (выплата ЗП).
- **NonCashOperationEntity** — журнал безналичной выручки/расходов (отдельно от сейфа, т.к. это не наличные).
- **NonCashSettlementEntity** — отслеживание того, что деньги с эквайринга падают на счёт не мгновенно, а с задержкой (`DelayDays`, настраивается из панели): статусы `InTransit → ArrivedUnconfirmed → Confirmed`.
- **ExpenseEntity** — расход (списание) наличных из сейфа или безнала, с опциональным фото подтверждения.

### Основной сценарий — закрытие смены (`RaportOperationsService.SendRaportAsync`)

1. Кассир (через клиент, говорящий по gRPC) присылает факт по кассе/безналу/сейфу, разбивку часов и минусов по сотрудникам смены (максимум `ShiftRules.MaxEmployeesPerShift` человек и `MaxHoursPerShift` часов суммарно).
2. Сервер под advisory-блокировками Postgres (сейф → сотрудники по Id, в фиксированном порядке — защита от deadlock) пересчитывает:
   - расхождение кассы/безнала против программных значений;
   - сколько наличных из кассы уходит в сейф (всё сверх `InitialCashRegister`);
   - разницу между заявленным и текущим балансом сейфа («уравнивание расхождения»);
   - ожидаемую сумму минусов сотрудникам — и требует, чтобы она сошлась с введённой.
3. Если у сотрудника уже отрицательная ЗП, для него отдельно проверяется лимит минуса (не больше `ставка × часы`).
4. Пишутся: отчёт, движения сейфа, движения ЗП по каждому сотруднику, запись безнала и запись ожидания эквайринга (`NonCashSettlementService`), опционально — фото (через `PhotoSessionStore`, привязанные к сессии, полученной ранее через запрос фото у сотрудника).
5. Итог отправляется в Telegram (тема отчётов + тема сейфа + личные темы сотрудников в зарплатном чате), баланс сейфа публикуется подписчикам (`SafeUpdatesNotifier`, gRPC-стрим) — строго после коммита транзакции, чтобы не показать клиенту цифру, которой ещё нет в БД.

### Прочие операции
- **AdvanceOperationsService** — аванс/выплата ЗП сотруднику, из сейфа или безналом; проверяет, что выплата не превышает текущий баланс ЗП (кроме принудительной выплаты из root-панели — `skipBalanceCheck: true`, туда сознательно можно уйти в минус).
- **InventoryOperationsService** — списание недостачи, поровну между выбранными сотрудниками (остаток от деления раздаётся по одному сотрудникам по порядку).
- **ExpenseOperationsService** — расход из сейфа или безналом, с отправкой в Telegram и опциональным фото.
- **NonCashSettlementService** — учёт задержки поступления эквайринга и ручное подтверждение прихода через root-панель (вкладка Settlement).
- **LedgerCompactionService** — фоновый сервис (раз в сутки): всё старше 1-го числа прошлого бизнес-месяца схлопывается в одну агрегированную запись на сейф и по одной на сотрудника. Балансы (`SUM`) не меняются, меняется только число строк — защита от бесконечного роста append-only журналов. Полная история хранится за текущий и прошлый месяц, архивом за более ранние периоды остаётся сама переписка в Telegram.

### Root-панель (`/root`, Razor Pages)

Собственная авторизация (`RootPanelAuthService`, access/refresh-токены, рейт-лимит на неудачные попытки логина), вкладки:
- **Force** — принудительный аванс/выплата ЗП сотруднику в обход обычных лимитов.
- **Inventory** — недостачи.
- **Raports** — история отчётов о сменах.
- **Salary** — корректировки и история ЗП по сотрудникам.
- **Settlement** — статус безналичных поступлений, настройка задержки эквайринга, ручное подтверждение прихода денег.
- **Employees** — список сотрудников.

### Конфигурация (см. `Smena/appsettings.json`)

Секреты (строка подключения, токен бота, ключ API, доступы МойСклад) в репозитории не хранятся — передаются через переменные окружения (`env_file` в docker-compose/stack-манифестах вне этого репозитория).

- `ConnectionStrings:Default` — строка подключения к Postgres.
- `Telegram:*` — токен бота, ID чата отчётов/расходов/сейфа, ID зарплатного чата, таймауты, опциональный SOCKS5-прокси (`ProxyUri`) для сетей, где Telegram заблокирован напрямую.
- `Photo:*` — таймаут ожидания фото от сотрудника и TTL фото-сессии.
- `RootPanelAuth:*` — TTL токенов панели и настройки рейт-лимита логина.
- `Warehouse:*` — интеграция с МойСклад (токен либо логин/пароль, лимит выборки).
- `ApiKey:Key` — ключ, которым gRPC-клиент аутентифицируется перед сервером (`GrpcApiKeyInterceptor`).

## Запуск

Docker-манифесты и env-файлы с секретами (`docker-compose.local.yml`, `stack-api.yml`, `api.env`, `api.local.env`) находятся не в этом репозитории, а в родительской deploy-папке, из которой он разворачивается — там же и актуальные инструкции по запуску.

В общих чертах:

- **Локально** — свой Postgres в контейнере, без прод-инфраструктуры; поднимается через `docker compose -f docker-compose.local.yml up --build`. Панель — `http://localhost:5000/root` (логин по умолчанию `root`/`root`), gRPC — `localhost:5001`.
- **Прод** — Docker Swarm сервис (`stack-api.yml`) поверх внешних сетей `edge-overlay` (proxy), `db-network` (Postgres) и `tg-socks` (прокси для Telegram), с volume под ключи Data Protection (иначе после пересоздания контейнера в swarm куки панели переставали расшифровываться).

## Структура репозитория

```
Smena/
  Program.cs                     — точка входа, маршрутизация gRPC/Razor по префиксам
  ApplicationServiceCollectionExtensions.cs — регистрация всех сервисов
  Protos/                        — контракты gRPC (raport, safe, employee, expense, advance, inventory, warehouse, ...)
  Services/Data/                 — EF Core: DbContext, сущности, advisory-локи, миграции
  Services/Operations/           — бизнес-логика (смена, сейф, ЗП, безнал, расходы, инвентаризация, компакция журналов)
  Services/Telegram/              — бот-клиент, общий поллер апдейтов, отправка сообщений
  Services/Photo/                 — запрос и временное хранение фото от сотрудника
  Services/Warehouse/             — интеграция с МойСклад
  Services/RootPanel/             — авторизация и инфраструктура админ-панели
  Pages/Root/                     — Razor Pages панели (вкладки Force/Inventory/Raports/Salary/Settlement/Employees)
  Migrations/                     — миграции EF Core
```
